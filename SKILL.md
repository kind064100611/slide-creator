# Slide Creator

Create slides from the user's prompt and supplied or retrieved material. Content is primary; templates only help present it.

When this skill has been loaded through the skill loader, its returned content is complete. Do not call `read_file` on this `SKILL.md` again in the same turn.

Keep partition notes, template choices, checks, and intermediate paths internal. After a successful conversion, return only a short source-grounded deck description and the Open slides card or link from the render result.

## Hard gates before any layout access

These gates are mandatory and apply before reading any file under `assets/layouts`:

- **Markdown slide-boundary gate:** determine the document's highest authored heading level among H1-H3: H1 when any H1 exists, otherwise H2, otherwise H3. Each heading at that boundary level starts exactly one source owner and one slide. Lower-level headings remain named regions inside that owner unless readable geometry requires a continuation. Persist the boundary-heading ledger and its total before catalog lookup. Never count nested H2/H3 headings as extra pages merely because they contain body text.
- Build the ordered source-owner manifest from those boundary headings first. Preserve every nested heading, paragraph, list, table, metric, and relationship as a distinct region under its owning boundary row.
- Never list, glob, or recursively search `assets/layouts`. After deriving every owner structure signature, read [assets/layouts/catalog.md](assets/layouts/catalog.md) once and retain only the candidate rows whose structural signals can satisfy each owner. Discard the full catalog text from later working state. Match by `sourceKind`, `dominantStructure`, `itemCount`, `directRegionCount`, `textRegionCount`, `headerMetadataCount`, `peerCount`, relationship topology, named semantic regions and parent paths, numeric-scale compatibility, table dimensions, chart shape, and connector edge count—not by title or business-topic string similarity. `itemCount` is the number of atomic source-owned display nodes after expanding table records and repeated nested groups; `directRegionCount` counts direct children; `textRegionCount` counts audience-facing containers. Exclude header metadata from body cardinalities.
- **`dashboard` classification gate:** `dominantStructure="dashboard"` is forbidden as a catch-all for a page that merely has numbers plus prose. It is legal only when the source explicitly has all four `dashboard` facts declared by the catalog: page-level assessment, peer headline-measure strip, numeric same-unit/same-scale comparison, and named supporting detail/action groups. Otherwise use the most distinctive retained fixed structure and its named region roles. A summary plus peer cards is still peers; a subordinate flow plus peer groups is still directed-flow. String or currency values, ratios with different units, labels, and prose must set `sameUnitComparison=false` and can never be bound to comparison-bar widths.
- Select exactly one final layout from that owner's retained catalog rows and record its absolute path. A candidate retained for another owner cannot be borrowed. After every owner is routed, read each unique final selected layout file exactly once. Do not read an unselected candidate. Retain only a compact structure summary: `data-layout`, placeholder names, repeatable-node declarations, optional selectors, connector topology, fixed regions, and style identity; do not replay the full file in later reasoning.
- **Single template checkpoint gate:** finish routing for the entire deck before reading any layout. Read every unique final selected path once, reuse its compact summary for every matching owner, then stop layout discovery. If `artifact_render` proves one selected layout record is incomplete, reread only that already-selected layout; do not inspect alternatives during recovery.
- Do not materialize the deck through repeated `write_file` calls. Those calls persist their complete HTML arguments in assistant replay and make every later LLM request larger. Keep only paths and structured ledgers during discovery, then perform one final atomic HTML-persist-and-render operation.
- If catalog evidence is insufficient to select one retained fixed layout, split only at a source-owned boundary or report the unmatched structure. Do not substitute a looser template or read candidate templates for comparison.
- Before calling `artifact_render`, compare the compact deck's ordered `sourceOwner` ledger with the manifest. Missing owners, combined sibling owners, changed order, or a record count below the manifest lower bound block rendering; `artifact_render` repeats the check on materialized `.slide[data-source-owner]` nodes.
- Before calling `artifact_render`, also reconcile an atomic **display-content** ledger for every owner. Record every audience-facing paragraph, list item, table row, metric row, named node, note, and conclusion exactly once, together with its final template region. Keep presentation-control, relationship-control, and asset-control instructions in a separate non-rendered control ledger. The count of populated repeated nodes must equal the count implied by the source and the selected template contract. A missing display item, rendered control text, a merged pair, a derived duplicate, an untraceable summary, or an empty required region blocks rendering even when the page count is correct.

For Markdown, only a heading at the resolved boundary level starts a new owner. Deeper headings are page-internal semantic regions and must stay with that owner unless a validated continuation is necessary.

## Required workflow

Complete these stages in order:

1. Partition the source by section.
2. Select a suitable style and layout for each slide.
3. Assemble and validate one compact ordered deck specification.
4. Call `artifact_render` once to read the selected files, materialize the HTML, validate it, and convert it to PPTX.

## 1. Partition by source section

Use the source heading hierarchy and order as the content plan.

Classify every source node before building the owner manifest or copying text:

- **Display content** is audience-facing material: authored titles, facts, measures, labels, explanations, conclusions, citations, and genuine figure captions. Only display content may enter visible template bindings.
- **Presentation control** tells the generator how to make the deck, for example which date to use, which style to apply, how to split pages, or what to omit. Apply it to generation behavior but never render it as a subtitle, note, card, footer, or callout.
- **Relationship control** states how authored nodes relate, for example "keep these three nodes connected" or "show the phases directionally." Use it to choose and populate a relationship-preserving layout; never render the instruction sentence itself.
- **Asset control** describes unavailable images, image omission, replacement, or extraction behavior. Omit that operational wording. Preserve a quoted caption only when it is independently audience-facing and factual rather than an instruction to the generator.

Record non-display nodes in a separate control ledger with their applied effect. Classification precedes the verbatim-copy rule: "preserve source wording" applies only to display content. If a sentence mixes audience facts with generation control, preserve the factual clause and apply—but do not display—the control clause.

Treat YAML front matter as source-owned presentation metadata, not body copy. Recognized footer metadata is `deck-footer`, `default-content-footer`, and `owner-footers`. Apply `deck-footer` to opening, contents, chapter-divider, and closing pages; apply `default-content-footer` to substantive pages; then apply an exact `owner-footers` heading match as the highest-priority override. This precedence is mandatory and must be checked as an exact page-by-page footer ledger immediately before rendering; chapter names, parent headings, layout names, or owner titles may not replace an applicable metadata value. Do not render these keys or values as body regions, and do not infer any unprovided footer label.

- Default to one slide for each boundary-level source section.
- Keep a section's heading, paragraphs, lists, tables, measures, conclusions, and subordinate groups together.
- Do not merge separate boundary-level sections merely to reduce page count.
- A lower-level heading with its own copy is a distinct region inside the current slide, not an automatic divider or extra page. Preserve its heading and body together.
- Create a section divider only when the source authors a boundary-level transition block or the user explicitly requests one. Do not synthesize divider pages from nested agenda entries.
- Split a section only when a populated suitable layout cannot show it at readable density without overflow, clipping, or overlap.
- Before splitting, use all available space in the owning slide and verify that the final layout was selected from the catalog rows using the section's complete structure signature. A split is invalid when the owning slide or its continuation is visibly sparse enough to hold the omitted compact groups.
- Continuation slides remain owned by the same section, use distinct source-grounded titles, preserve source order, and contain non-overlapping content.
- A substantive section—including the first—owns its heading and all subordinate content; never turn that heading into a separate cover or divider.
- Create a cover, contents page, section divider, or closing page only from a distinct source block explicitly authored as that presentation boundary, or when the user requests it. Otherwise omit it. Render each substantive section once, except for necessary continuation slides.

Before layout selection, create an internal **source-owner manifest**. Give every boundary-level section one ordered owner row containing its exact source heading, source kind (`opening`, `contents`, `chapter-boundary`, `substantive`, or `closing`), atomic display-item count, direct-region count, header-metadata count, peer count, exact parent path for every nested group, explicit relationship signature, numeric-scale compatibility, and planned slide count. Nested headings contribute regions and item counts to that owner, not additional owner rows. Never replace distinct boundary rows with one combined row or reduce the manifest to a desired deck length.

Compute and persist the manifest lower bound before catalog routing as `boundary-level owners + required continuations`. Record the boundary level, ordered owner headings, continuation count, and total in file-backed state. A later plan may add necessary continuations but may never omit or merge a boundary owner. Immediately before rendering, count the compact deck records and compare their ordered `sourceOwner` values with the manifest; a lower count blocks `artifact_render`, which repeats the check after materialization.

For a Markdown source, record the resolved boundary level once and require every manifest owner to use that level. Same-level headings at the boundary are peer owners; lower-level headings remain ordered child regions under the nearest boundary owner.

Normalize numbering only while matching agenda entries to top-level headings; retain the exact authored heading in the manifest. Assign every unique display-content item to exactly one manifest row, record every control item separately, and assign every planned slide to exactly one owner row. A continuation may repeat the owner key with a continuation suffix, but it must not absorb a peer owner. The ordered owner count is a hard lower bound on the generated page count unless an owner is explicitly marked optional by the source.

Do not start layout selection until the manifest proves that every authored boundary and substantive section has an owner, every unique item maps to one visible region, explicit graph/table/sequence relationships are recorded rather than flattened into prose, and the owner rows follow source order.

### Content fidelity

- Never invent facts, owners, dates, measures, relationships, categories, or actions to fill a template.
- Treat Markdown as audience-meaningful source material, not as serialized template bindings. Keep facts in grammatical sentences, ordinary lists, and semantic tables. Do not split one natural statement into artificial label/value/unit/caption bullets, add field-name headings, repeat a metric in multiple source bullets, or rewrite prose merely to reveal the intended template. Value/unit separation and visual-role assignment happen only in the compact generation bindings after routing. One source sentence may populate the value, unit, caption, and supporting-copy roles of the same canonical visual item; this is role decomposition, not permission to invent or repeat a second semantic item.
- Treat usable display-content wording as finished copy. Preserve it whenever it fits; shorten only the smallest span that prevents readable layout.
- Preserve every unique fact, name, number, unit, time range, qualifier, uncertainty, provenance, conclusion, action, hierarchy, sequence, and explicit relationship.
- Preserve at least one exact visible occurrence of every authored display token. Do not silently append, remove, normalize, or reformat a unit, sign, inequality, range mark, ordinal, prefix, or suffix merely because a surrounding heading or chart scale implies it. When one natural sentence is decomposed into multiple visual roles inside the same semantic item, a supporting prose role may restate the already-preserved metric grammatically (for example, an exact `+316%` value with “up 316%” in its supporting sentence), but it must not change meaning or create a second fact. Keep numeric geometry values separate from visible labels.
- Preserve display-content wording verbatim unless the user explicitly asks for summarization, rewriting, or translation. Do not render presentation-control, relationship-control, or asset-control wording merely because it appears in the source. Do not replace audience-facing sentences with polished paraphrases, expand a terse source node into an inferred explanation, or add a generated takeaway. Layout selection and fitting operate on authored display content; they do not authorize content rewriting.
- Insert source characters into DOM text exactly once. Escape reserved HTML characters once during serialization; never pre-escape source text and then escape the entity string again. Visible text such as `>98%` must render as `>98%`, never as `&gt;98%`.
- Preserve authored paragraph and list-item boundaries. Do not split one source paragraph into multiple sibling paragraphs, merge independent paragraphs into one text node, or convert prose into bullets merely to fit a card. A fixed layout must accept the source node boundary or be rejected.
- Let CSS perform ordinary line wrapping. Do not insert `<br>` elements or hard line breaks inside source prose unless the source explicitly authors that break; manual wrapping changes PPTX text runs and becomes unstable across renderers.
- Preserve source structure: peer items remain peers, table rows remain rows, and connected nodes remain distinct nodes with the source-supported connection.
- A heading owns all subordinate paragraphs, lists, tables, and nested headings until the next peer or higher-level heading. Do not lift a trailing paragraph into a page-level conclusion, merge a nested label into its parent heading, or repeat a parent grouping label inside each child.
- Page-level metadata such as a year, date, reporting period, data period, unit, or source line is not a narrative lead, peer-group heading, or standalone content node. Keep it in the title/header metadata region unless the source explicitly gives it substantive prose semantics.
- Consecutive same-level headings under one source owner are same-kind peer items unless the source explicitly introduces different named groups or a relationship between them. Different paragraph/list lengths do not create primary/supporting tiers, and the last peer does not become a conclusion merely because it appears last.
- Template slot names, table column headers, parser field names, and inferred roles are not slide copy. Do not surface generic labels such as `Summary`, `Result`, `Metric`, `Strategic meaning`, or `Assessment method` unless the source authors that visible text.
- Keep authored label, value, caption, and body nodes distinct when their separation carries grouping or emphasis. Do not concatenate them into a replacement sentence or split one authored title token into decorative fragments.
- Preserve inline emphasis and its punctuation at the same semantic location. An authored prefix such as `**ESOP:**` remains a bold `ESOP:` prefix; do not flatten the emphasis, drop the colon, or promote the prefix into a new heading.
- When a graph or diagram already renders authored edges, prose that only serializes those same edge triples is relationship metadata, not a second visible note group. Render the named nodes and edges once; do not duplicate the edge ledger as body copy unless the source adds independent explanation.
- Preserve the authored order of nodes inside each owner. A template does not authorize moving a value ahead of an earlier list, moving a caption below an unrelated body, or pinning the final note away from its preceding evidence.
- Preserve source emphasis: a stated anchor result, headline measure, or governing node must remain visually primary instead of becoming an ordinary peer card.
- Give each fact or action one primary visible region. Remove semantic duplicates within and across slides without deleting unique evidence, qualifiers, or actions.
- Every slide body must contribute content owned by its source section.
- Exclude navigation, site chrome, every control-ledger item, generation instructions, and unsupported pure images from slide copy. Immediately before rendering, search visible bindings against the control ledger; any match blocks rendering.

## 2. Select style and layouts

Use [assets/document-shell.html](assets/document-shell.html) as the external document shell for every deck. The default generated HTML and PPTX style is the external `assets/styles/webex-dark.css`; use another style only when the user or source metadata explicitly requests it. A light reference PDF or standard HTML is not, by itself, a request to copy that theme. Do not read or inline either file during normal generation; `artifact_render.deck` reads them client-side.

Style and layout have separate ownership. The selected document style exclusively owns the slide/canvas background, color scheme, global typography, theme variables, rail, and deck-wide header/footer treatment. A layout template owns only its content topology, content-region geometry, and the component surfaces inside that topology. Therefore a layout style block must not set a page or canvas `background`, global `color`, `font-family`, or theme variables, and must express content surfaces and text through the selected style's semantic variables such as `--panel-background`, `--panel-2`, `--ink`, `--muted`, `--panel-line`, `--line`, and `--accent-*`. Never copy a reference HTML's light canvas or palette into a layout template. Run the static layout validator after editing any template; a theme-ownership failure blocks generation.

Before choosing a layout, derive a compact semantic structure signature from the source content itself. It must explicitly record the owner, source kind, dominant structure (`narrative`, `peers`, `comparison`, `table`, `hierarchy`, `branching`, `directed-flow`, `timeline`, `state`, `architecture`, or `dashboard`), atomic peer/item count, direct-region count, header-metadata count, peer count, audience-facing text-region count, relationship kind (`none`, `peer`, `comparison`, `directed`, `hierarchy`, `branching`, `timeline`, or `state-transition`), named semantic regions with exact cardinalities and parent paths, numeric-scale compatibility, table row/column counts, and connector edge counts when present. Count every table record and every repeated nested node. A page with one subordinate authored flow is `directed-flow`, not `hierarchy`, unless the source actually authors parent-child containment or fan-out. A summary plus peer evidence is `peers` or a named composite, not `comparison`, unless exactly two direct subjects share aligned dimensions. Topic nouns and business wording are evidence only for labels, never for layout selection. Do not require or add generation-only layout instructions to the source document.

Preserve the source's semantic regions and top-level cardinality. Distinct peer items remain distinct, ordered stages remain connected in order, hierarchy levels remain nested, and table records remain rows. Supporting facts may be placed inside those source-owned regions, but do not add, merge, or remove regions merely to fit a template.

A layout is one invariant slide skeleton, not a collection of slots to assemble freely. Its region types, hierarchy, reading order, visual hierarchy, and connector topology remain fixed. Extensibility means only that a layout-declared homogeneous collection may contain more or fewer peer nodes by duplicating or removing the same node fragment. Repeated nodes keep the same class, visual treatment, semantic role, and relationship to the rest of the skeleton. Never combine fragments from different layouts, insert a new region type, turn peers into stages, or change connector endpoints to accommodate content.

Do not reject an otherwise exact layout merely because the source has a different number of homogeneous peer nodes than an example. Node cardinality is routing evidence, not a hard template count, whenever the layout declares that node class repeatable. Emit the full authored collection as direct children of the declared repeat container and let the selected slide template's own grid/flex rules reflow it. A layout file must never contain a nested `<template>` fragment or embed another layout. Split at a source-owned boundary only when the expanded peers cannot meet the geometry and readability floors; never cap the collection, drop peers, or switch to a looser template solely because the count changed.

Derive one compact structure signature for every owner, read [assets/layouts/catalog.md](assets/layouts/catalog.md) once, and route each owner independently from those semantic fields. Apply every applicable **Reject when** condition before choosing one final layout path for each manifest row. A row retained for another owner is not automatically eligible. Match required primitives and relationship structure before capacity or density: a table requires table rows, and a hierarchy or directed flow requires its declared connector-preserving layout rather than generic cards. After routing all owners, read only the unique final layout files and reduce them to compact summaries. The catalog is the semantic decision index; the selected layout file supplies exact columns, repeated elements, optional regions, connectors, and geometry markers.

For every manifest row, make an internal routing record containing the source structure signature, shortlisted catalog rows, every applicable **Reject when** result, the selected layout, and its absolute path. Apply rejection conditions before preference or reuse. A layout used on an adjacent slide, or a layout that can merely contain all words, is never a positive matching signal. When one retained fixed structure matches the full source signature, select it even if a looser layout looks more generic; `dashboard` never outranks exact topology. Reusing one complex layout for structurally different owners is a routing warning that must be resolved before assembly.

Choose the final layout from the retained catalog rows based on the assigned content. Do not change, omit, merge, or reorder content to make a layout fit. If no retained fixed layout matches, split only at a source-owned boundary or report the missing structure; never force-fit a looser template. Make the final choice before reading any layout file; do not read candidate layouts for comparison.

When a section contains a table followed by sibling headings, lists, notes, controls, or conclusions, the table is only one source region. Inventory and render the following siblings as additional regions; do not treat the first table as the whole section, and do not select a table-only layout unless the section has no substantive non-table siblings.

Classify the section's dominant structure before choosing a layout. An explicit timeline, directed sequence, hierarchy, branching relationship, state transition, comparison, table, or quantitative scale requires a matching retained structure-preserving layout. Fitting all words into generic cards is not a valid substitute for the source relationship.

Treat heading levels as structural evidence. A governing H2 followed by repeated H3 branches and later independent H2 notes is a root-to-branches hierarchy with a peer note stack, even when the Markdown does not contain arrows. Conversely, four H3 peers followed by an ordinary `Summary` are peer cards with a takeaway, not ordered controls with an overall goal. The `ordered-control-grid-goal-band` layout is eligible only when every control has a source-authored local goal/direction and the final band is explicitly an overall goal/target. A quantified-loss page with a lead fact strip, homogeneous loss cards, a compound multi-metric support group, a separate recovery-cost group, and a page warning must preserve those distinct schemas; it is not a generic two-tier metric grid.

Distinguish peer groups from sequences before using arrows. Numbered headings, enumerated actions, or repeated cards are peers unless the source states time order, dependency, causality, transition, or authored arrows. Use directed-flow layouts only for those authored relationships; otherwise preserve the items as peer columns, peer cards, or hierarchical branches.

Treat dashboard-like sections as composites when metric labels, comparison labels, and sibling explanatory or action headings appear together. Preserve headline KPIs, comparison/evidence regions, and supporting detail regions on the same owned slide or continuation; do not collapse the structure into undifferentiated cards.

When a chart, tree, flow, or map is dominant, preserve its source-authored supporting notes, controls, conclusions, or side panels in the same slide region set unless a readable split is impossible.

Treat an explicit region ratio or asymmetric composition such as 60/40, 70/30, or 2:1 as a structural constraint. Select a fixed catalog layout whose own skeleton preserves that ratio and region topology. If none exists, split at a source-owned boundary or add a characteristic fixed layout; never route arbitrary content through a generic mixed-content composition.

Reject a candidate layout when one of its required regions or connectors has no source-owned meaning. A specialized layout may preserve a relationship that exists in the source, but it must not introduce a flow, hierarchy, comparison, or grouping merely to fill the template.

Instantiate exactly one selected layout for each slide by using that layout file's canonical slide body and canonical `style[data-layout-style]` block. A `data-layout` name is not template use: do not recreate the page with custom DOM, substitute class names, move layout-scoped CSS into a global style block, or restyle the canonical skeleton. Replace placeholders only. For each layout-declared homogeneous collection, emit direct child items that satisfy the repeat container's item tag/class contract and ordered role classes; do not create a nested template, reusable fragment, secondary layout, or newly designed child schema. Remove only layout-declared optional regions. Every repeated collection must preserve the template container's `data-layout-repeat`, exact `data-layout-count`, item tag/class contract, ordered item-role classes, role tags, and materialization attributes; a repeated slot is not permission to emit arbitrary child markup. Populate each fixed slot from the matching source node without synthesizing a visible field label. Reflow repeated peers through the template's own grid or flex rules; do not create new wrappers, panels, rows, sidebars, bands, or mixed component types. Do not override a template's structural grid, column assignment, region ratio, visual hierarchy, or connector geometry with inline CSS. When the source does not fit the selected invariant skeleton, split the source-owned section at a valid source-owned boundary; never read, invent, rename, or substitute another layout after inspection, and never mutate or compose the template. Do not leave sample copy or invent decorative subtitles, pills, callouts, labels, or footer text.

Before filling any slot, make a per-owner atomic binding ledger in memory from the Markdown: one entry for each heading, paragraph, list item, table cell, metric token, ordinal, and relationship. Assign every entry to exactly one declared template slot, or to one explicit decomposition whose visible fragments reconstruct that entry without semantic rewriting. Do not turn one source entry into both a headline value and a repeated explanatory sentence; after extracting a value or label, the other slot receives only the unconsumed source fragment. Do not add glue labels such as `Evidence 1`, `Focus`, `Overall goal`, or `Conclusion` unless those exact labels are authored. Do not replace an authored governing heading with a sibling metric. Do not paraphrase content that already fits: shorten only when geometry requires it, retain the original subject and all qualifiers, and never change or duplicate a number, sign, unit, ordinal, named entity, or relationship. A terminal action/note that the selected template assigns to `FOOTER_NOTE` is consumed by the footer and must not also appear in a body list, scorecard, callout, or card. Immediately before assembly, reconcile the ledger so every entry is consumed once, no visible fragment is generated without an entry, and footer-only content is not also present in a body slot.

Materialize functional geometry explicitly. A dedicated ordinal badge must be emitted as the template's text-bearing badge node with both `data-pptx-shape` and `data-pptx-text`; never rely on inherited span styling for centering. Every connector must use the template's explicit shaft and arrowhead nodes. SVG `marker`, `marker-start`, `marker-mid`, and `marker-end`, CSS pseudo-elements, and Unicode arrow glyphs are forbidden for functional arrowheads because they do not survive all PPTX materializers reliably. Preserve the template's separator ownership: one group divider stays one divider and must not be copied onto every peer item. Compact local comparison bars must keep the template's bounded comparison region instead of stretching into unused page width.

Every slide record must carry the selected template path and a `sourceOwner` equal to its exact source-owner heading text. `artifact_render` preserves the template's `data-layout`, canonical skeleton and canonical style block, and writes the exact `data-source-owner`. The Markdown `#` prefix is syntax and may be omitted; heading wording, punctuation, numbering, and order may not change. Continuations append a stable continuation suffix. Bind only declared placeholders, and put repeated same-kind node fragments inside the declared collection binding. Do not send layout CSS, fixed skeleton markup, deck-specific CSS, freehand generic cards, or a parallel slide shell. Do not write review manifests, generation records, comparison declarations, or validator verdicts into `examples/`; normal generation has no reference artifact and consumes none of those files.

## 3. Assemble and validate compact slide records

Build one ordered compact deck specification in source order. Each record instantiates exactly one selected layout using only declared bindings, homogeneous repeated-node fragments, and optional-region removals. Keep full HTML and CSS out of the request; `artifact_render` reads the shell, style, and unique selected layouts from their paths and materializes the self-contained HTML deterministically.

1. Put the selected style into the document shell.
2. Include each selected layout's complete style block once.
3. Insert every populated slide fragment into the shell.
4. Keep one 16:9 `.canvas` per slide and the footer as its final, bottom-pinned child.

Validate the compact deck before conversion; `artifact_render` then validates the materialized HTML before writing either output:

- no unresolved placeholders, duplicate IDs, remote resources, mojibake, empty table rows, sample copy, or unsupported optional nodes;
- the ordered `.slide[data-source-owner]` ledger covers every source-owner manifest row exactly once except declared continuations; a missing owner, combined peer owners, duplicated owner, unexpected owner, or owner-order mismatch blocks conversion;
- the generated page count is not below the manifest lower bound; never add implicit cover, contents, divider, or closing pages around the boundary-level owners;
- no slide contains body regions sourced from more than one manifest owner; a subtitle, summary card, support card, or footer that names or paraphrases another peer owner is evidence of an illegal merge;
- perform this owner-ledger and record-count check immediately before `artifact_render`; do not rely on an earlier plan or visible text coverage as a substitute;
- every slide's `data-layout` is present in its routing record, its layout path was read once after selection, and no selected layout violates an applicable catalog rejection condition;
- every substantive source section appears in order;
- no primary fact, action, qualifier, or relationship is missing, invented, or repeated;
- every visible numeric/sign/unit token has the same source multiplicity after legitimate display decomposition; a headline metric repeated again in its note is a failure unless the source itself contains that second occurrence;
- every generated visible phrase is either exact source wording or a geometry-required shortening that preserves the source subject, predicate, qualifiers, and measures; stylistic paraphrase is not allowed;
- every source-owner atomic display-content ledger reconciles exactly: source-only count `0`, generated-only count `0`, merged-item count `0`, changed-parent count `0`, and rendered-control count `0`; a display paragraph moved into a subtitle, support card, footer, or sibling node is `changed-parent` even when the words remain visible; for a template that declares exact cardinalities, report and verify those cardinalities explicitly before rendering;
- every subtitle must map to an authored subtitle field for that exact owner; never promote an ordinary paragraph, conclusion, card heading, or support-node title into the subtitle merely because the selected template exposes one; omit an optional subtitle when no authored subtitle exists;
- the final footer ledger matches the metadata precedence exactly on every page: owner override, else default content footer for substantive pages, else deck footer for authored presentation-boundary pages;
- no section stops at its first table when later sibling headings, lists, notes, controls, or conclusions are present;
- every explicit relationship is visible through separate repeated nodes and the selected layout's connectors, axis, rows, or branches—not only through prose, punctuation, Unicode arrows, or DOM order;
- authored ordinal prefixes, mathematical signs, units, comparison qualifiers, and compact separators inside labels or values remain visible and exact; do not replace `01 ·`, `−`, `<`, `>`, `q/q`, `·`, `/`, or `:` with a different notation merely for style;
- when a layout renders an authored ordinal in a dedicated number/index region, do not repeat the same ordinal in the adjacent title text;
- dedicated ordinal text is centered on both axes inside its badge and carries both materialization attributes;
- each functional connector has one explicit continuous shaft and one explicit arrowhead attached at the target endpoint; no SVG marker or Unicode arrow substitutes it;
- on a `0 0 100 100` connector viewBox, each attached arrowhead remains a compact terminal triangle no wider than `.7` viewBox units and no taller than `1.4`; a filled fan, ribbon, floating head, or mid-line head is invalid;
- divider count and ownership match the selected template, including a single lead-to-group separator rather than per-peer separators;
- compact comparison or progress tracks remain inside the selected template's bounded local region and do not expand to dominate the slide;
- visible text remains readable and source-grounded;
- no shape is stretched, collapsed, clipped, overlapped, outside the canvas, or intruding into fixed header and footer regions, and ordinary content slides do not compress all populated regions into a narrow middle band with large unused space above and below;
- no text overflows its container or crosses a divider;
- repeated peer elements remain balanced;
- every footer remains at the bottom of the slide.

When validating a locally materialized HTML deck, run `node scripts/validate_layouts.cjs --require-source-owner <generated.html>` and treat only exit code `0` with `{"status":"passed"}` as success. A model-authored checklist, visual spot check, or self-reported contract pass is not evidence. Any missing repeated-item role class, item wrapper, item tag/class, declared count, canonical style block, canonical skeleton relation, or source owner must be corrected before review or conversion.

Normal slide generation must not read [references/slides-review.md](references/slides-review.md), an adjacent standard HTML, or a reference PDF. Those inputs are external review evidence, not generation context. Load and apply `slides-review.md` only when the user explicitly asks to compare, audit, review, or validate a generated deck against an identified reference. In that explicit review workflow, run `node scripts/validate_review_records.cjs <reference.html> <candidate.html>` so evidence is derived from the complete current artifacts, then inspect every rendered page pair at readable full-slide scale; a contact sheet, generic layout-lint pass, sampled pages, or hand-written review declaration cannot qualify the deck. Treat page structure, hierarchy, node cardinality, connectors, content ownership, and visual mass as authoritative; theme differences and unsupported pure-image pixels are not failures. Keep any optional saved report outside `examples/` and never feed it into generation.

The footer's visual structure comes from the selected style. Its text is optional and must come from distinct content owned by that slide or from a source-authored note explicitly scoped to the whole deck. Repeat a footer note across slides only when the source itself marks it as deck-wide; render that note only in the footer, never duplicate it into a card, scorecard, summary, or other body region. Never infer or hardcode a footer, and never move a deck/slide title, measure, conclusion, or ordinary body sentence there. The structural right slot may contain the generated page counter using unpadded ordinals such as `1 / 18`; otherwise leave it empty unless the source supplies suitable slide-owned or explicitly deck-wide footer text.

When the fixed template includes a left footer label and the source provides no recognized footer metadata and no separate footer sentence, use an authored identity without inventing copy: the exact deck title for opening/divider/closing pages, and the exact current source-owner heading for substantive pages. This is a fallback only; it must never override `deck-footer`, `default-content-footer`, or `owner-footers`. Do not leave the label blank while dropping that authored identity from the page chrome.

Resolve only the `{{current_local_date}}` token as the local calendar date in `YYYY-MM-DD` form. Preserve every authored character around the token: for example, `Prepared {{current_local_date}}` must become `Prepared 2026-09-19`, not only `2026-09-19`. Do not change it to a long month-name format or a different timezone date.

Header chips and pills are content regions, not decoration. Populate them only with labels or measures owned by the current source section. A label or measure owned by a nested subsection, card, scorecard, table, or other body region must remain there and must not be hoisted into the slide header. Do not import risk labels, dates, counts, owners, or other metadata from another slide merely because a header slot is available; remove an unsupported optional chip or pill instead.

Use the generic HTML geometry validation available in the render path. When validation identifies a bad slide, regenerate only that slide by first removing unsupported optional content. If the selected invariant layout still cannot fit, split the owning source section at a valid source-owned boundary. Reassemble and validate the complete document after the correction.

## 4. Generate PPTX

For a newly generated deck, verify the compact deck record count equals the manifest total, then call `artifact_render` with `deck`, a valid `.html` basename in `htmlFileName`, `sourceMimeType: text/html`, `outputFormat: pptx`, and a valid `.pptx` filename. The deck contains only document paths/metadata and compact slide records; it never contains shell CSS, layout CSS, or a complete generated HTML document. For a deck generated from local Markdown, always pass the original absolute Markdown path in `sourcePath`; the render boundary independently enforces the boundary-level owner ledger and page floor while keeping lower-level headings inside their owners. Use `contentPath` only when a complete HTML file already existed before this turn. If rendering reports an owner-ledger, binding, selector, page-floor, geometry, materialization, or conversion failure, preserve the exact error, correct only the named owner in the local compact deck, and retry `artifact_render` until it returns valid paths. Make at least 10 focused correction attempts before treating the failure as unrecoverable. Do not reread the full Markdown, catalog, or unrelated templates, create a separate conversion pipeline, emit a generic apology, or claim success before the tool succeeds.

If `artifact_render` is unavailable, stop after validated HTML and report PPTX generation as blocked. Never substitute Playwright screenshots, PptxGenJS, office automation, or another conversion path.

## Source and output constraints

- For local PDF and Confluence input, use the textual content exposed by the available reader. Pure photographs, screenshots, illustrations, and unavailable source images may be omitted; do not create empty image regions.
- Keep HTML self-contained: no remote fonts, network resources, `@import`, CSS `url(...)`, or unsupported local image paths.
- Replace a visible date placeholder with the current local date at generation time; never hardcode a generated date into a reusable template.
